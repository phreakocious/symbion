Set up symbion in this project. Write nothing before the user approves it. Keep scratch files out of the repo.

Facts, gathered as this skill loaded (run any command left unrun):
- symbion: !`symbion -V 2>&1 || echo "symbion: not installed"`
- the repo: !`git rev-parse --show-toplevel 2>/dev/null || echo "not a git repository"`

1. Say in two sentences what symbion is: a notebook and ticket registry kept beside the repo, in a git repo of its own; each new session starts with the open bugs, tasks and questions, and a trap filed on a file reaches the agent when it opens that file. Then say what setup does: install the CLI if needed, make the project's store, bring in its open threads, and open the browser view.
2. If the repo line above is not a path, say that the store needs a git repository, and stop.
3. The CLI. Under Antigravity, `operation not permitted` from symbion is agy's sandbox, not a missing install: run each symbion call with `BypassSandbox` until step 4's rules are in. This plugin needs symbion 0.16.0 or later (a `.devN` counts), on Python 3.11 or later. Not installed: plan `uv tool install --python '>=3.11' 'symbion[gui]'` when `uv` is on PATH (uv may download a Python; say so), else `pipx install 'symbion[gui]'`, with `--python` naming a 3.11 or later when `pipx environment --value PIPX_DEFAULT_PYTHON` is older. Older: plan `uv tool upgrade symbion` or `pipx upgrade symbion`, whichever installed it. With neither uv nor pipx, say so, point to https://github.com/phreakocious/symbion#install, and stop. Never run pip into a system Python.
4. The store. With the CLI installed, run `symbion init`, without `--yes`: it lists each change and makes none. Under Antigravity, every `symbion init` in this skill takes `--agent antigravity`, so its list names the rules agy's auto mode needs: show them, and ask the user to add each at agy's `/permissions` before approving: a rule may name a store not made yet, and the rest of setup then runs with no prompt. Never write agy's settings yourself. Under Hermes, every `symbion init` takes `--agent hermes`, which links the skill into Hermes's profile. Show that list, less its notes on the plugin. Without the CLI, say what it does by default: it creates the store `../<repo>-notes`, a git repo beside this one, and writes nothing into this repo. Setup itself adds one line, `- We use symbion for durable notes and tickets.`, to the instructions file this host reads. Claude Code reads `CLAUDE.md`. Hermes reads the first of `.hermes.md`, `AGENTS.override.md`, `AGENTS.md` and `CLAUDE.md` it finds: add the line there, else create `AGENTS.md`. Antigravity never reads `CLAUDE.md`: add the line to `AGENTS.md` or `GEMINI.md`, whichever exists, else create `GEMINI.md`, since a new `AGENTS.md` would hide `CLAUDE.md` from Pi and Hermes. Where that file is gitignored or someone reviews every change to it, propose the line instead of writing it.
5. Ask for approval of steps 3 and 4 at once. First list, in your message, one line per write: the exact install command and where it puts the CLI, the store's path, and the instructions file with its line. A question dialog alone hides them. The store is outside this repo, so the host may ask before its writes too. On no, stop: nothing was written. On yes, install, then run `command -v symbion`. If it finds nothing, the install's bin dir is not on PATH: say where the command went, use its full path for the rest of setup, and ask before any change to a shell's rc file (`uv tool update-shell`, `pipx ensurepath`); the hooks find symbion only in a session started from a shell whose PATH has it, and under Hermes only in a gateway started from one. Then, in a call of its own, run `symbion init` again without `--yes`. If its list differs from what you described, show the difference and ask again. Under Antigravity, next run `symbion -V` without `BypassSandbox`: if it fails, ask the user to add the rules init lists, and wait; once it starts, in auto mode, take `BypassSandbox` only for what `adoption.md` reads outside the repo. Then run `symbion init --yes` and append the line, after a newline if the file lacks a final one.
6. Adoption, empty store or not. Run `symbion skill adoption` and follow it, leaving out what an entry holds. If `symbion list --limit 1` shows an entry, first ask whether to look for what the store lacks (notes kept before the plugin, a handoff since); if the user says no, go to 8. Scout the TODO files, handoff notes, agent memory and the git log since the last handoff, then build the candidate table and the list of sources to retire, naming each file and what happens to it. Print both in full in your message, then ask for approval. On yes, add the entries as one `symbion add --from-json -`, retire the sources as `adoption.md` says, and run `symbion commit`. On no, keep the store as it is and say that `/symbion:setup` runs adoption again.
7. If the store is still empty, say so, and send the user to https://symbion.nullphase.net/ to see a store that weeks of work filled.
8. Start `symbion serve --no-browser` in the background with its output to a temp file, and read its first line, the URL, with `head -1`. Give the user that URL to look through the store, and say that `symbion serve --stop` stops it and every other serve.
